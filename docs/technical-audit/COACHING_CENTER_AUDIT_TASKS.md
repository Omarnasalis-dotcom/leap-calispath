# Coaching Center Audit — Task List

Findings from a full audit of the Coaching Center feature (Program Builder, Warrior Program, My Clients, Client Dashboard, Progress Tracking, Exercise Library). Critical items in this list were verified exploitable against a local Supabase instance, not just theoretical.

## 🐞 Coach-Reported Bugs

- [x] **Add a "rest between rounds" input for circuit/superset straight sets** — `src/components/coaching/BlockConfigWizard.tsx`. Added a "REST BETWEEN ROUNDS (SECONDS)" input, shown under the same condition `useWarriorTimer.ts:252` actually consumes `rest_after_round` (`timing_system === 'straight_set' && structure !== 'single'`), initialized from `initialMetadata.rest_after_round` and carried through the `onChange` payload — also fixes the bonus finding (editing an existing block no longer wipes its saved rest value). Typecheck clean. Not yet manually verified in the simulator.
- [x] **Fix day focus tag not surviving a template reload** — `src/hooks/coaching/useProgramBuilder.ts:372-378` (`loadExistingTemplate`). Now reads `parsed.metadata.focus_tag` (already parsed one line earlier per block) back into the `ProgramDay` object at the moment the day is first created during load, so it round-trips correctly. Typecheck clean. Not yet manually verified in the simulator.
- [x] **Fix tabata blocks showing a default "10 REPS" badge instead of work/rest info on the warrior side** — `src/components/coaching/WarriorExerciseRow.tsx`. Moved the `timing_system === 'tabata'` check ahead of the circuit/superset check in the ternary chain, matching the already-correct ordering in `WarriorBlockCard.tsx` and `BuilderExerciseRow.tsx`. Typecheck clean. Not yet manually verified in the simulator.

## 🔴 Critical

- [x] **Add ownership check to `delete_coach_week_data` RPC** — `supabase/migrations/20260614102615_remote_schema.sql:954-979`. No check that the caller owns the template. **Verified exploitable**: an unrelated coach account successfully deleted another coach's program block. Fixed in `supabase/migrations/20260628190000_fix_delete_coach_week_data_ownership.sql` (owner-or-admin check) — re-tested attacker-blocked / owner-succeeds / admin-override all pass locally.
    - [x] **Add ownership check to `delete_coach_client_data` RPC** — `supabase/migrations/20260614102615_remote_schema.sql:901-951`. No check that the caller owns the `warrior_programs` assignment being deleted. Fixed in `supabase/migrations/20260628191000_fix_delete_coach_client_data_ownership.sql` (owner-or-admin check) — re-tested attacker-blocked / owner-succeeds / admin-override all pass locally.
- [x] **Add ownership check to `assign_program_template` RPC** — `supabase/migrations/20260614102615_remote_schema.sql:781-827`. Takes `p_coach_id` from client input with no check it matches the caller; can silently reassign another coach's client. Fixed in `supabase/migrations/20260628192000_fix_assign_program_template_ownership.sql` (owner-or-admin check on `p_coach_id`) — re-tested impersonation-blocked / owner-succeeds / admin-assigns-on-behalf-of-coach all pass locally, including the existing "force-complete previous active program" logic still working correctly. Note: this only locks down who the assignment is attributed to — it does not restrict which `p_template_id` can be cloned from; that's covered separately by the "Restrict `program_templates` SELECT RLS" task below.
- [x] **Fix `workout_logs` RLS tautology** — `supabase/migrations/20260614102615_remote_schema.sql:4006-4013`, policy "Users can view relevant workout logs". `wp.warrior_id = wp.warrior_id` should be `wp.warrior_id = workout_logs.warrior_id`. Currently lets any coach with ≥1 client read every warrior's logs platform-wide. Fixed in `supabase/migrations/20260628193000_fix_workout_logs_rls_tautology.sql` — re-tested with two fully unrelated coach/warrior pairs: Coach A can no longer read Warrior B's logs (direct query returns empty), Coach A still sees their own client's logs, and warrior self-access is unaffected.
- [x] **Restrict `program_templates` SELECT RLS** — currently `using (true)` for any authenticated user; should scope to owning coach or assigned warrior. Fixed in `supabase/migrations/20260628194000_restrict_program_templates_select.sql`. Admins were already covered by a separate pre-existing "Admin manages all templates" policy, so the replacement just scopes to `coach_id = auth.uid()` or an assigned warrior (`warrior_programs.warrior_id = auth.uid()`). Re-tested 5 scenarios locally: unrelated coach blocked, owning coach OK, assigned warrior OK, admin OK, and the exact embedded-join query `WarriorProgramScreen.tsx` uses (`warrior_programs?select=...,program_templates:template_id(...)`) still works.
- [x] **Restrict `program_blocks` SELECT RLS** — same `using (true)` issue as above. Fixed in `supabase/migrations/20260628195000_restrict_program_blocks_select.sql`. Unlike `program_templates`, this table already had three correctly-scoped policies ("Coaches manage blocks", "Admin manages all blocks", "Warriors can read their program blocks") that the permissive policy was silently overriding — so the fix was just dropping the redundant one, no replacement needed. Re-tested 4 scenarios locally: unrelated coach blocked, owning coach OK, assigned warrior OK, admin OK.
- [x] **Restrict `exercise_library` UPDATE/DELETE RLS** — policy "Coaches and admin can manage exercises" has no `created_by = auth.uid()` check; any coach can edit/delete exercises they didn't create (UI hides this, DB doesn't enforce it). Fixed in `supabase/migrations/20260628196000_restrict_exercise_library_ownership.sql` — split the single `FOR ALL` policy into INSERT/UPDATE/DELETE, with UPDATE/DELETE scoped to `created_by = auth.uid()` or admin. Legacy rows with `created_by IS NULL` remain editable by any coach (rather than locking everyone but admins out of pre-existing catalog entries). SELECT and INSERT behavior unchanged. Re-tested 8 scenarios locally: cross-coach update/delete blocked, owner update OK, admin delete OK, legacy null-creator row editable by any coach, non-coach blocked from update/insert, normal coach insert still works.

## 🟠 High

- [x] **Wrap `handleSaveTemplate` in a transaction/RPC** — `src/hooks/coaching/useProgramBuilder.ts`. Added `save_program_template` RPC (`supabase/migrations/20260629100000_add_save_program_template_function.sql`) that does the template upsert + block diff/delete + block/exercise upsert atomically; client now builds the flattened blocks payload and makes one `supabase.rpc()` call instead of N sequential table calls. Deliberately `SECURITY INVOKER` (default) so existing RLS keeps enforcing ownership — no new auth logic to audit. Re-tested locally: new template create, edit (remove/update/add blocks), cross-coach block (NOT_FOUND), admin override (success) all pass. This also resolves the FK-violation item below, since both were the same code path. **Bonus finding (not fixed, out of scope)**: `program_templates`'s INSERT RLS policy only checks `coach_id = auth.uid()`, not `is_coach = true` — confirmed any authenticated non-coach account can create their own template.
- [x] **Wrap `handleToggleBlockStatus` delete+insert in a transaction** — `src/screens/coaching/WarriorProgramScreen.tsx`. Added `toggle_block_status` RPC (`supabase/migrations/20260629101000_add_toggle_block_status_function.sql`, `SECURITY INVOKER` — relies on the existing "Warriors manage own logs" RLS policy rather than re-implementing ownership checks), takes the client's local-midnight boundary as a parameter so day-boundary semantics don't shift to server time. Also added a `togglingBlockIds` in-flight guard in the screen plus a `disabled`/dimmed state on the checkbox in `WarriorBlockCard.tsx`, closing the double-tap race the audit flagged. Did **not** add a DB unique constraint on `workout_logs` — risked colliding with the separate "Add Log" flow (`WarriorLogModal`) which may intentionally allow multiple log entries per block per day; out of scope for this fix. Re-tested locally: full completed→missed→none cycle, a log from a different day is left untouched by today's toggle, and an unrelated authenticated user attempting to toggle someone else's block is correctly rejected by RLS (`42501`).
- [x] **Surface the swallowed FK-violation error in block delete** — `src/hooks/coaching/useProgramBuilder.ts:924-930`. Fixed as part of the `save_program_template` RPC above: blocks that can't be deleted (workout_logs attached) are now collected server-side and returned as `undeletable_block_ids`; the client shows an `Alert` telling the coach how many blocks were kept and why, instead of silently doing nothing. Re-tested: block with an attached `workout_logs` row is correctly kept (and reported) while the rest of the save succeeds.
- [x] **Add KeyboardAvoidingView to `ExercisePickerModal.tsx`** — has a search `TextInput`, same bug class as `WarriorLogModal.tsx`. Fixed with the same `KeyboardAvoidingView` + `TouchableWithoutFeedback` pattern. Typecheck clean. Not yet manually verified in the simulator.
- [x] **~~Add KeyboardAvoidingView to `CopyBlockModal.tsx`~~ — not applicable.** Investigated: this modal has zero `TextInput` fields anywhere — it's entirely selection lists and buttons (pick a target, confirm). There's no keyboard that could ever appear, so there's nothing to avoid. The original audit note assumed it shared the bug class without checking; no fix made.
- [x] **Fix timer completion routing in `WarriorTimerModal`/`useWarriorTimer`** — `src/hooks/useWarriorTimer.ts`. Narrowed down the real bug: AMRAP and tabata both routing through the generic `onAmrapComplete` is actually harmless today (`WarriorProgramScreen.tsx`'s `onAmrapComplete` and `onBlockComplete` handlers are byte-for-byte identical), so that part wasn't an active bug. The real one: a for-time block hitting its **time cap automatically** called the generic `onAmrapComplete` instead of the dedicated `onForTimeComplete(blockId, elapsedSeconds)` — only the manual "COMPLETE" button tap used the correct callback, so auto-completion lost the elapsed-time prefill on the log modal. Added `onForTimeComplete` as a proper hook parameter and routed both the foreground-tick and background-resync time-cap branches through it instead. Typecheck and test suite clean. Not yet manually verified in the simulator (requires a for-time block with a short time cap to trigger naturally).

## 🟡 Medium

- [x] **Scope `loadMasterTemplates`'s block-count query to the current coach** — `src/hooks/coaching/useProgramBuilder.ts:153-187`. Now filters `program_blocks` to `template_id in (...)` using the coach's own template ids fetched just above, instead of reading every row in the table. Typecheck clean.
- [x] **Wrap `CopyBlockModal`'s copy operations in a transaction** — `copyBlockToClient`/`copyDayToClient`/`copyDayToTemplate`. Added `copy_block_to_template` and `copy_day_to_template` RPCs (`supabase/migrations/20260629102000_add_copy_block_day_functions.sql`, `SECURITY INVOKER` — relies on existing `program_blocks`/`block_exercises` RLS for ownership) that insert a block (or day's worth of blocks) plus their exercises atomically; the client now makes one `supabase.rpc()` call per copy action instead of a loop of block-insert + exercises-insert pairs. Applied to local and production. Not yet manually verified in the simulator.
- [x] **Verify caller identity server-side instead of trusting route params** — `app/my-clients.tsx`, `app/client-dashboard.tsx` read `coachId`/`isAdmin`/`templateId`/`warriorId` from URL params with no server-side ownership check on the route itself. Investigated rather than patched: the route params only affect what `MyClientsScreen`/`ClientDashboardScreen` *request*; what's actually *returned or mutated* is bounded by the RLS and RPC ownership checks already added in the 🔴 Critical section (`program_templates`/`program_blocks` SELECT RLS, and the `delete_coach_week_data`/`assign_program_template` ownership checks). Verified live against local Supabase with two unrelated coach accounts: Coach B forging `isAdmin=true` with no `coachId` filter still can't see Coach A's templates; Coach B calling `delete_coach_week_data`/`assign_program_template` with Coach A's forged `templateId`/`coachId` is rejected server-side ("Not authorized..."). No code change needed — the underlying RPCs/RLS, not the route params, are the actual security boundary.
- [x] **Add confirmation dialog before deleting a shared exercise** — `src/screens/coaching/ExerciseLibraryScreen.tsx`. `handleDeleteExercise` now takes the exercise name and prompts before deleting, using the same `Platform.OS === 'web' ? window.confirm(...) : Alert.alert(...)` pattern already used elsewhere in the coaching center (`useProgramBuilder.ts`'s `handleDeleteTemplate`/`handleDeleteWeek`). The message calls out that the exercise is shared and may be used in other coaches' programs. Typecheck clean.
- [x] **Make `handleLogWorkout`'s timeout actually abort the request** — `src/screens/coaching/WarriorProgramScreen.tsx`. Replaced the `Promise.race` against a bare timeout (which only abandoned the promise — the insert could still land server-side after the "failed" UI fired) with a real `AbortController` wired through `.abortSignal()`, matching the convention already used in `TrialService.submitResult`. Verified locally that an aborted request actually rejects with `AbortError` instead of completing in the background. Also removed a now-meaningless empty-bodied `if (err.message?.includes('timed out'))` block left over from the old approach (one of the three spots flagged in the 🟢 Low "vestigial empty-bodied conditionals" item below).
