# Coaching Center Audit — Task List

Findings from a full audit of the Coaching Center feature (Program Builder, Warrior Program, My Clients, Client Dashboard, Progress Tracking, Exercise Library). Critical items in this list were verified exploitable against a local Supabase instance, not just theoretical.

## 🐞 Coach-Reported Bugs

- [ ] **Add a "rest between rounds" input for circuit/superset straight sets** — `src/components/coaching/BlockConfigWizard.tsx:169-191`. The wizard has a "TARGET ROUNDS" field for circuit/superset structures but no field for `rest_after_round`, even though that field exists in `ConceptMetadata` (`src/lib/BlockConceptParser.ts:13`) and defaults to `'90'` wherever a new block is created (`src/hooks/coaching/useProgramBuilder.ts:534,550,622,944`). Coaches have no way to see or edit it, so every circuit/superset block silently uses a 90s default. Bonus finding: the wizard's `onChange` payload (lines 39-71) never carries `rest_after_round` forward at all, so opening the wizard on an *existing* block and changing anything wipes its saved rest value back to nothing.
- [ ] **Fix day focus tag not surviving a template reload** — `src/hooks/coaching/useProgramBuilder.ts:372-376` (`loadExistingTemplate`). When a template is loaded into the builder, each block's `focus_tag` is correctly parsed from its metadata (line 361), but the `ProgramDay` object built right after never reads it back into `day.focusTag` — it's simply left unset. The tag is still saved in the DB (every block in the day carries `metadata.focus_tag`, written correctly at save time per lines 945-949), so this is a read-back bug, not a data-loss bug — but it looks identical to data loss from the coach's perspective, especially right after assigning a template to a client and reopening it.
- [ ] **Fix tabata blocks showing a default "10 REPS" badge instead of work/rest info on the warrior side** — `src/components/coaching/WarriorExerciseRow.tsx:152-171`. Root cause is a branch-order bug: `BlockConfigWizard.tsx:41` always sets `structure: 'circuit'` for tabata blocks, and `WarriorExerciseRow.tsx`'s circuit/superset check (line 152) runs *before* its dedicated tabata check (line 165) — so tabata exercises always match the circuit branch first and render the generic `REPS: {exercise.reps}` badge, where `exercise.reps` is just the blanket `'10'` default every new exercise gets (`useProgramBuilder.ts:451`), instead of the intended "Xs WORK / Ys REST" badge. Confirmed this is warrior-side only: the block-level header (`WarriorBlockCard.tsx:178,197`) and the coach-side builder row (`BuilderExerciseRow.tsx:58`) both check `timing_system === 'tabata'` first and render correctly — only `WarriorExerciseRow.tsx` has the checks in the wrong order.

## 🔴 Critical

- [x] **Add ownership check to `delete_coach_week_data` RPC** — `supabase/migrations/20260614102615_remote_schema.sql:954-979`. No check that the caller owns the template. **Verified exploitable**: an unrelated coach account successfully deleted another coach's program block. Fixed in `supabase/migrations/20260628190000_fix_delete_coach_week_data_ownership.sql` (owner-or-admin check) — re-tested attacker-blocked / owner-succeeds / admin-override all pass locally. Still needs to be pushed to production.
- [x] **Add ownership check to `delete_coach_client_data` RPC** — `supabase/migrations/20260614102615_remote_schema.sql:901-951`. No check that the caller owns the `warrior_programs` assignment being deleted. Fixed in `supabase/migrations/20260628191000_fix_delete_coach_client_data_ownership.sql` (owner-or-admin check) — re-tested attacker-blocked / owner-succeeds / admin-override all pass locally. Still needs to be pushed to production.
- [x] **Add ownership check to `assign_program_template` RPC** — `supabase/migrations/20260614102615_remote_schema.sql:781-827`. Takes `p_coach_id` from client input with no check it matches the caller; can silently reassign another coach's client. Fixed in `supabase/migrations/20260628192000_fix_assign_program_template_ownership.sql` (owner-or-admin check on `p_coach_id`) — re-tested impersonation-blocked / owner-succeeds / admin-assigns-on-behalf-of-coach all pass locally, including the existing "force-complete previous active program" logic still working correctly. Note: this only locks down who the assignment is attributed to — it does not restrict which `p_template_id` can be cloned from; that's covered separately by the "Restrict `program_templates` SELECT RLS" task below. Still needs to be pushed to production.
- [x] **Fix `workout_logs` RLS tautology** — `supabase/migrations/20260614102615_remote_schema.sql:4006-4013`, policy "Users can view relevant workout logs". `wp.warrior_id = wp.warrior_id` should be `wp.warrior_id = workout_logs.warrior_id`. Currently lets any coach with ≥1 client read every warrior's logs platform-wide. Fixed in `supabase/migrations/20260628193000_fix_workout_logs_rls_tautology.sql` — re-tested with two fully unrelated coach/warrior pairs: Coach A can no longer read Warrior B's logs (direct query returns empty), Coach A still sees their own client's logs, and warrior self-access is unaffected. Still needs to be pushed to production.
- [x] **Restrict `program_templates` SELECT RLS** — currently `using (true)` for any authenticated user; should scope to owning coach or assigned warrior. Fixed in `supabase/migrations/20260628194000_restrict_program_templates_select.sql`. Admins were already covered by a separate pre-existing "Admin manages all templates" policy, so the replacement just scopes to `coach_id = auth.uid()` or an assigned warrior (`warrior_programs.warrior_id = auth.uid()`). Re-tested 5 scenarios locally: unrelated coach blocked, owning coach OK, assigned warrior OK, admin OK, and the exact embedded-join query `WarriorProgramScreen.tsx` uses (`warrior_programs?select=...,program_templates:template_id(...)`) still works. Still needs to be pushed to production.
- [x] **Restrict `program_blocks` SELECT RLS** — same `using (true)` issue as above. Fixed in `supabase/migrations/20260628195000_restrict_program_blocks_select.sql`. Unlike `program_templates`, this table already had three correctly-scoped policies ("Coaches manage blocks", "Admin manages all blocks", "Warriors can read their program blocks") that the permissive policy was silently overriding — so the fix was just dropping the redundant one, no replacement needed. Re-tested 4 scenarios locally: unrelated coach blocked, owning coach OK, assigned warrior OK, admin OK. Still needs to be pushed to production.
- [x] **Restrict `exercise_library` UPDATE/DELETE RLS** — policy "Coaches and admin can manage exercises" has no `created_by = auth.uid()` check; any coach can edit/delete exercises they didn't create (UI hides this, DB doesn't enforce it). Fixed in `supabase/migrations/20260628196000_restrict_exercise_library_ownership.sql` — split the single `FOR ALL` policy into INSERT/UPDATE/DELETE, with UPDATE/DELETE scoped to `created_by = auth.uid()` or admin. Legacy rows with `created_by IS NULL` remain editable by any coach (rather than locking everyone but admins out of pre-existing catalog entries). SELECT and INSERT behavior unchanged. Re-tested 8 scenarios locally: cross-coach update/delete blocked, owner update OK, admin delete OK, legacy null-creator row editable by any coach, non-coach blocked from update/insert, normal coach insert still works. Still needs to be pushed to production.
