# Static World Audit — Task List

Findings from a full audit of the Static World feature (`StaticWorldScreen`, `StaticService`, `staticLogic.ts`, the `static_holds`/`statics_assessments` tables, and every file that imports from or references Static World — `AssessmentEngine`, `WorldSelectorGrid`, `ProfileScreen`, `clashLogic`, `leaderboard.ts`). This is an audit only — nothing in this list has been fixed yet. Severities follow the same scale used in `COACHING_CENTER_AUDIT_TASKS.md`.

One finding below (🔴 Critical) is **not Static-World-specific** — it was discovered while tracing how `static_holds`/`profiles.statics_tier` writes are protected, but it's a platform-wide `profiles` table vulnerability that affects every world, not just Static. It's listed first because of its severity. It was verified exploitable against a local Supabase instance, not just theoretical.

## 🔴 Critical (platform-wide, not Static-specific)

- [x] **`profiles` UPDATE RLS allowed any authenticated user to overwrite any other user's profile row** — Fixed in `supabase/migrations/20260629130000_lock_down_profiles_and_tournament_participants_rls.sql`, which drops the `"Tournament service can update rewards"` policy (`for update to authenticated using (true) with check (true)`) entirely. Investigating *why* that policy existed led to two more related findings, fixed in the same pass:
  - **`payout_tournament(p_user_id, p_gp_reward)` had no authorization or validation at all** — any authenticated user could call it directly with an arbitrary user id and amount and mint unlimited `tournament_gp`/`glory_score` for anyone, completely independent of whether a tournament existed or ended (the same impersonation-style bug class as the earlier `submit_trial_result` fix, but with no bound on the amount at all). Dropped entirely (`20260629131000_add_tournament_conclusion_rpcs.sql`) and replaced by `conclude_rank_based_tournament`/`conclude_knockout_tournament`, which compute the payout server-side from each tournament's own data (idempotent via a row lock + status check) instead of trusting a client-supplied amount.
  - **`tournament_participants` had the same `using(true) with check(true)` pattern** (`"Allow participants to update each other"`) — any authenticated user could set `final_rank`, `is_eliminated`, `scores`, or `total_score` on any other participant's row. Dropped, with a new `guard_tournament_participant_protected_fields()` trigger (mirroring `guard_profile_protected_fields`) blocking `final_rank`/`is_eliminated` changes from anyone but the new SECURITY DEFINER RPCs — closing the gap where a participant could otherwise still set those two fields on their *own* row directly (row-level RLS alone doesn't restrict columns). `scores`/`total_score` remain self-only-writable via the pre-existing `"Warriors can update own scores"` policy, unaffected.
  - Cross-user writes that legitimately need to happen (marking match losers eliminated, marking deadline non-submitters eliminated, assigning final ranks, paying out) now go through new RPCs — `auto_eliminate_non_submitters`, `eliminate_tournament_match_losers`, `conclude_rank_based_tournament`, `conclude_knockout_tournament` — that re-derive the legitimate outcome from trustworthy server-side data (deadlines, scores, already-recorded match results) rather than trusting client-submitted final values. `TournamentService.ts` rewired to call these instead of writing those rows directly.
  - **Known residual gap, not fixed by this change**: `tournament_matches` (`"Allow all update"`, `using(true)` for `public`) and `tournament_sessions` (`"Allow authenticated users to update sessions"`, any authenticated user) still have the same wide-open pattern. `conclude_knockout_tournament` still trusts its `p_winner_user_id` parameter (validated only as "is a participant in this session," not as "actually won their matches"), so a sufficiently motivated attacker could still tamper with `tournament_matches.winner_id` to fraudulently advance through a knockout bracket — though they can no longer mint arbitrary currency once there, since the payout itself is now capped/idempotent/rank-derived. Tracked here for a dedicated follow-up; deliberately scoped out of this pass since fixing it means redesigning match-winner determination and round advancement, not just RLS.
  - The original `guard_profile_protected_fields` trigger remains in place as defense-in-depth for the fields it covers (`is_admin`, tiers, points, etc.) and is unaffected by this change.

## 🟠 High

- [x] **No anti-cheat ceiling proportional to movement difficulty, and no submission cooldown, on `submit_static_hold`** — Fixed in `supabase/migrations/20260629120000_add_static_movements_and_attempts_tables.sql` + `20260629121000_refactor_static_functions_for_movements_table_and_cooldown.sql`. Added a `static_movements` reference table with a per-movement `max_hold_seconds` ceiling (replacing the flat 300s bound), a `static_hold_attempts` log table (since `static_holds` only stores PBs, giving a cooldown nothing to check otherwise), and a 30s per-movement submission cooldown inside `submit_static_hold` itself — mirroring the trial system's cooldown pattern without needing a new edge function. Verified locally: ceiling/cooldown/invalid-id/negative-time all reject with distinct error codes (`P1001`–`P1004`), a different movement can be submitted immediately after one is rejected/accepted (per-movement, not global), and rejected attempts are correctly *not* logged (so the cooldown can't self-extend forever). **Note:** the 12 `max_hold_seconds` values are final, provided directly by the product owner per movement (not the inverse-multiplier-scaled placeholders used during design).

## 🟡 Medium

- [x] **`AssessmentEngine` treats Static World as unlocking at tier 4, while every other gate in the app says tier 1** — `src/lib/AssessmentEngine.ts:22-24` (`getWeakestWorld`, comment: "haven't unlocked... Static (tier 4)") and `:82-84` (`getTestsForTag`'s `validStatic` filter requires `strengthTier >= 4`). Meanwhile `src/lib/staticLogic.ts:58-60` (`isStaticWorldUnlocked`), `src/components/profile/WorldSelectorGrid.tsx:50` (`unlockTier: 1`), and `app/_layout.tsx:104` (`tierLocks['static-world'] = 1`) all agree the real unlock is tier 1. Net effect: a tier 1–3 user can navigate to and log holds in Static World just fine, but the coaching center's auto-recommend feature (`AssessmentEngine.generateRecommendations`, used by `WarriorProgramScreen`/`WarriorProgramSections`) will never suggest a Static movement for that user — it behaves as if the world doesn't exist for them yet. Looks like a stale assumption left over from a since-lowered unlock tier.
- [x] **No `LIMIT`/pagination on any of the three Static leaderboard RPCs** — `get_static_movement_leaderboard`, `get_static_level_leaderboard`, and `get_static_well_rounded_leaderboard` (all in `20260614102615_remote_schema.sql`) return every user who has ever logged a hold, unbounded. By contrast, `get_global_well_rounded_leaderboard` (the cross-world WRA leaderboard) caps at `LIMIT 100`. Same class of issue as the coaching audit's "scope the query" findings — fine today, won't scale.
- [ ] **`get_static_well_rounded_leaderboard()`'s `RETURNS TABLE` doesn't include the per-category hold times the client expects** — the SQL function returns `u_id, d_name, hs_pts, fl_pts, bl_pts, pl_pts, t_score, rnk, country, gender` only, but `StaticService.getWellRoundedLeaderboard()` (`src/services/StaticService.ts:167-170`) maps `e.hs_time`/`e.fl_time`/`e.bl_time`/`e.pl_time` into `handstand_time`/`front_lever_time`/`back_lever_time`/`planche_time` on every `StaticWellRoundedEntry`. Those source fields don't exist, so the four `_time` fields are always `0`. Currently harmless because nothing in `StaticWorldScreen.tsx` renders them — but it's a broken contract waiting to surface a bug the moment someone wires up a UI that does.
- [x] **Movement IDs and their point multipliers were duplicated across four places that had to be kept in lockstep by hand** — Fixed alongside the anti-cheat work above: the three SQL-side `CASE` statements (`submit_static_hold`'s multiplier lookup, `sync_static_points`'s and `get_static_well_rounded_leaderboard`'s category-bucketing) are now consolidated into one `static_movements` reference table that all three functions JOIN against (`20260629120000_add_static_movements_and_attempts_tables.sql` + `20260629121000_refactor_static_functions_for_movements_table_and_cooldown.sql`). The client-side `STATIC_MOVEMENTS` array in `staticLogic.ts` is intentionally left as a parallel copy (client/server split is fine — the goal was eliminating the 3x SQL-side duplication, not the language split).

## 🟢 Low

- [ ] **`StaticService.getUserStats`'s zero-initialization is dead code** — `src/services/StaticService.ts:131-147`. The `import('../lib/staticLogic').then(({ STATIC_MOVEMENTS }) => { STATIC_MOVEMENTS.forEach(m => pbs[m.id] = 0); })` is fired but never awaited, so it almost always resolves after the function has already returned `{ pbs }`. In practice this is harmless today only because every caller (`AssessmentEngine.generateRecommendations` via `WarriorProgramScreen.tsx:396-407`) reads with a defensive `pbsStatic[m.id] || 0` fallback — but the code as written doesn't do what its own comment claims, and is one refactor away from actually mattering.
- [ ] **`src/lib/leaderboard.ts`'s `getStaticMovementLeaderboard`/`getStaticLevelLeaderboard` are fully unused** — they duplicate, via direct `.from('static_holds')` queries instead of RPCs, what `StaticService.getMovementLeaderboard`/`getLevelLeaderboard` already do. Zero call sites found anywhere in `app/` or `src/`. Dead code that could confuse a future reader into thinking there are two different/competing leaderboard data paths.
- [ ] **`statics_assessments` table is fully orphaned** — has its own columns (`handstand_variant`, `front_lever_hold`, etc.), correctly-scoped self-only RLS (`"Warriors manage own statics assessments"`), but zero references anywhere in client code. Looks like a leftover from an earlier design (a dedicated Static assessment step, parallel to the main `AssessmentScreen`) that was abandoned in favor of the simpler PB-tracking `static_holds` model.
- [ ] **`profiles.statics_tier` is a misleading name** — it stores a continuous points total (sum of peak per-category points, e.g. `47.5`), not a discrete tier index like `strength_tier` (0–9). Every place that reads it (`ProfileScreen.tsx`, `CoachScreen.tsx`, `AssessmentEngine.ts`, the WRA RPCs) already treats it correctly as points, so this is purely a naming-clarity issue, not a functional bug — but the name actively invites a future "tier" mixup.
- [x] **`ProfileScreen`'s self-healing points sync only catches "never synced," not "incorrectly synced"** — `src/screens/ProfileScreen.tsx:256-262` only re-runs `sync_static_points` when `profile.statics_tier === 0 || profile.statics_tier === null`. If a sync ever ran with stale multiplier data (see the duplication finding above) and produced a wrong-but-nonzero value, this safety net would never catch or correct it.
- [ ] **Minor theoretical race in the manual prep-countdown logic** — `StaticWorkoutLogModal` in `src/screens/StaticWorldScreen.tsx:698-751` runs both an `AppState` listener and a 250ms `setInterval`, and both independently compute elapsed time and can call `startTimer(...)` near-simultaneously (e.g., if the app is foregrounded right as the interval also ticks). `useTimer.start()`'s `if (isRunning) return` guard doesn't protect against this because both calls can read the pre-update `isRunning` value before React re-renders. Currently harmless — both calls compute nearly identical `elapsed`/`baseSeconds` values, so the duplicate call is idempotent in practice — but it's a fragile pattern, not a designed-safe one.
- [ ] **`manualInput`/`setManualInput` state is declared but never rendered** — `src/screens/StaticWorldScreen.tsx:69`. No `TextInput` bound to it exists anywhere in the component; looks like leftover state from a removed or never-finished "manually type in your hold time" input path (the modal is timer-only today).
- [ ] **`sql_archive/static_world_schema.sql` is a stale, unreferenced historical artifact** — a "run this in your Supabase SQL Editor" manual-setup script that predates the migration-based schema and isn't loaded or referenced by any code, config, or other doc. Harmless as long as no one mistakes it for current, but it's exactly the kind of file that does mislead someone searching the repo for "static_holds schema" months from now.
